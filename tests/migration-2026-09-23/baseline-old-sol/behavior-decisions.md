# Pre-migration behavior decisions (old skills, Sol baseline)

## Scope and method

This is a bounded comparison of the supplied backup skills, not an execution of the deep-review workflow. Routing guidance came only from:

- `backup/deep-project-review/SKILL.md`, `references/runtime.md`, and `references/templates.md`
- `backup/adaptive-model-orchestrator/SKILL.md` and `references/collaboration-and-validation.md`
- the synthetic case definitions in `backup/deep-project-review/tests/cases.json` and `migration-cases.json`

Historical expected answers and prior result files were not used. All decisions below are synthetic unless explicitly marked as an actual check. No subagent was spawned and no hypothetical repair was performed. Model IDs and effort values are the old skills' requested routes; they are not claims that a model was actually launched or that an effective configuration was verified.

## Migration routing cases under the old orchestrator

| ID | Decision | Requested model / effort and conditions |
|---|---|---|
| M01 | Delegate only if doing so has net coordination value; otherwise the main session can do it directly. | `gpt-5.6-luna` + `medium`. Escalate to `high` only for a real reasoning difficulty after checking source ambiguity, permissions, inputs, and validation evidence. If sources conflict or require interpretation, move that judgment to `gpt-5.6-sol` + `medium/high`. |
| M02 | This is an independent, plan-ready implementation task, so delegation is reasonable when a slot is available and ownership is isolated. | `gpt-5.6-terra` + `medium` by default; use `high` for demonstrably complex implementation. Provide stable inputs, file boundaries, interface, and acceptance checks. |
| M03 | Route by root-cause and impact, not by the two-line patch size. Do not start writing until the shared authorization contract, baseline, allowed scope, unique owner, and acceptance/regression checks are defined. | `gpt-5.6-sol` + `high`; use `xhigh` if a specific hard reasoning issue persists. Escalate to `gpt-6-astra` `high/xhigh` for a systemic design conflict or repeated failure. |
| M04 | Do not create a redundant requirements-understanding branch. The main session already has the requirements and the only remaining work is a tightly serial small edit; perform it directly and validate it. | No child model requested. If the main session's effective model is unavailable from host evidence, record it as unknown rather than inventing a route. |
| M05 | The current tool declaration is the stronger present capability signal; the stale cache is only historical catalog evidence. An actual suitable call may request `gpt-6-sol` + `high`. Before a successful call and trusted evidence, claim only that the host advertises support, not that execution or effective configuration succeeded. | Requested: `gpt-6-sol` + `high` once launched. Effective: not yet established. Preserve the call result and runtime/contract evidence after launch. |
| M06 | Diagnose the `model unavailable` failure. Do not silently replace it or record the failed requested configuration as successful. For generic orchestration, use an available model only if the task does not require Luna, state the substitution and limitation, and validate the output. | Requested failed: `gpt-6-luna` + `high`. Effective: none for that call. A substitute's exact model/effort must be recorded as its own requested/effective pair. |
| M07 | Use context isolation with a curated complete handoff: preserve the user's exact key correction, relevant original wording, constraints, files, and acceptance criteria. Keep source material paths available. | `fork_turns: none`, `model: gpt-6-sol`, `reasoning_effort: high`. Full-history mode cannot satisfy the requested override, so do not use it and do not rely on a model name inside the prompt. |
| M08 | Independent verification cannot be done by the same fixer. It may use the same model family in a newly created, context-independent agent if that is the best route and the agent did not perform the fix. | For cross-module repair validation, a separate `gpt-5.6-sol` + `high` agent is valid. The requested state is whatever model ID/effort appeared in the structured call; effective model and effort are unknown/unverified. | Since the host neither guarantees adoption nor exposes trusted metadata, the fixed-config deep review cannot be declared complete. When no safe, in-scope, useful ready work remains, wait using bounded completion notifications instead of inventing work or polling repeatedly. | Existing child routes remain as actually requested. Waiting does not require a model change. Integrate each result at a safe point when its dependency becomes ready. |

Consolidate tightly coupled work in the main session when that reduces coordination cost. | No override can truthfully be requested in the only fork mode. Do not claim a prescribed three-model run. Any workflow with a fixed model gate, such as deep review's Astra/xhigh stage, is blocked on this host. |
| M12 | Treat this as an environment failure. Fix or report the output-directory permission/path issue, then retry at the same justified reasoning level. | Keep `gpt-6-luna` + `high` if a retry remains useful; increasing effort cannot make a directory writable. Do not escalate models until logs show a reasoning or capability problem rather than environment failure. |

Every other W/T/M entry is a decision over a supplied synthetic scenario; no agents, fixes, model calls, or acceptance runs were performed for those scenarios.
